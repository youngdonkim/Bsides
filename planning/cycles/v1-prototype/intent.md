# 출처 스토리

## 자기 경험 — Bsides 발의자(본인) · 2026년 봄, 미미로그 출시 직후

미미로그라는 짧은 일상 로그 → 어학 학습 콘텐츠 생성 앱을 만들고 구글 플레이에 출시하면서 한 가지를 확신했다. 이제는 LLM 기반 코딩 에이전트(클로드 코드, 코덱스)와 디자인 에이전트(클로드 디자인)를 이용해 **혼자서도 웹·앱·데스크톱 애플리케이션 출시가 가능**하다는 것 — 의지와 노력이 있는 누구나 가능하다는 뜻이기도 하다. 그러나 "LLM이 만들어 주는 그럴듯한 쓰레기"가 아니라 **인간 전문가의 터치와 감성 한 스푼**이 필요하다는 것도 같이 깨달았다. 출시 후 부족함을 느낀 영역: 아이템을 초기에 **검증·발전시킬 사람**, **디자인 질**을 끌어올릴 사람, **자동화 하네스 능력**을 가진 개발자, **홍보·마케팅**을 함께 해줄 전문팀. 미미로그는 출시는 했지만 홍보·마케팅 계획을 세우지 못하고 있다 — 자금이 들어가는 결정이라 사이드 프로젝트로는 쉽게 결단이 안 난다. 서로의 전문성으로 도우면 비용도 줄고 결과 질도 올라가지만, **함께할 사람을 구하기가 어려워** Bsides의 필요를 느꼈다.

## 타인 대화 — 함께하는 디자이너 1명 · 현재 진행 중인 워크샵 참가자

이 분은 디자이너로서 **자신만의 서비스를 출시하고 싶은 욕구**가 강하고, **LLM 이용법을 배우고 싶은 욕구**도 강하다. 그래서 본인(Bsides 발의자)에게서 클로드 코드로 웹 서비스를 만드는 수업을 듣고 있다. 자기 전문성(디자인)을 실습 중인 서비스에 적용해서 LLM이 만들어준 디자인에 사람의 감성 한 스푼을 더해 질을 올릴 예정. **"수업 + 자기 서비스 출시"의 결합**이 이 분의 니즈.

# 문제 정의

LLM으로 혼자 출시까지 가능해진 솔로 메이커가, 한 분야는 잘해도 다른 분야(검증·디자인·자동화 하네스·홍보)는 부족한 상황에서, **서로의 전문성을 교환할 동료 커뮤니티가 없어 "그럴듯한 초고" 수준을 넘는 출시 품질로 끌어올리지 못한다**.

# 타겟 사용자

design 결과(Bsides.html "이런 분에게") 반영:

- **사이드 프로젝트 지망 직장인**
- **출시 의지 있는 디자이너·개발자·마케터·기획자** (프리랜서 포함)

공통 **상태**:

- ✅ LLM을 이용해 **직장 업무 자동화** 또는 **자신에게 필요한 서비스 구현**(예: 오픈 클로처럼 자기만의 자비스) 경험이 있음
- ✅ LLM에 관심이 많고, **사이드 잡 또는 창업을 위해 LLM 사용법을 더 깊이 배우고 실제로 출시해보고 싶은** 의지가 있음

즉, LLM 활용 기본기와 자기 손으로 뭘 만들어본 경험이 있는, **출시 의지 있는 직장인·프리랜서 메이커** 층.

# 사용 맥락

서비스 사용은 **두 형태**로 나뉜다.

## A. 워크샵 (제품 핵심 활동) — ✅ 확정

- **화상 워크샵**: 평일, 구글 미트 기반, **회당 약 1시간**.
- **오프라인 워크샵**: 주말, **회당 약 3시간**. 멘토·객원 멤버 간 직접 만남·연락처 교환.
- **부수 산출물 (강의 콘텐츠)** ✅:
    - **raw**: 수업 **녹음 또는 메모**.
    - **가공**: LLM으로 결과 콘텐츠(글) + AI 이미지 생성 서비스로 이미지화.
    - **게시**: 홈페이지에 **진행상황 정적 페이지로 그때그때 추가**. → 공개. 객원 모집·검색·외부 공유의 콘텐츠 자산이 됨(H2와 연결).

## B. 홈페이지 (워크샵 진입 funnel + 쇼케이스)

홈페이지에는 **두 사용자 그룹**이 있고 v1에서는 비대칭이 크다.

### B-1. 기존 멤버 (v1 기준 본인 + 워크샵 진행자 약 2명) ✅

- **홈페이지 사용 거의 없음**. 일상 소통·운영은 **카톡** 등 외부 채널.
- 운영 콘텐츠(공지·진행 결과 쇼케이스) **업데이트 시** 정도만 들름. 어쩌다 한 번.
- → 즉 v1엔 **멤버 로그인·대시보드·관리자 UI 같은 내부 사용 화면이 사실상 불필요**.

### B-2. 외부 잠재 객원 멤버 (v1 핵심 사용자) ✅

- **주된 시점**: 본업 외 시간(평일 저녁·주말). 알음알음 소개·검색·외부 링크 공유로 처음 들어옴. **객원 멤버 신청 결정** 시점.
- **빈도·세션 길이**: 🟡 첫 방문 1회 + 결정 전 1~2회 재방문 정도. 한 세션 5~10분 추정. *확인 필요*
- **환경**: **반응형 웹**(데스크톱·모바일 둘 다). 연결성 안정. ✅
- **결정 포인트**: **"이 릴레이 멘토의 서비스 구현 워크샵에 객원 멤버로 신청할까?"** — 멘토·과거 출시 사례·**진행상황 정적 페이지(강의 콘텐츠 누적)**·운영방식 검토. ✅

→ 외부 방문자가 **첫 방문 5분 안에 "이게 뭐고 신청은 어떻게"를 이해**해야 함. 이게 v1 홈페이지의 핵심 설계 조건.

→ web(반응형) 우선, 모바일 앱은 v1에 불필요. 멤버 로그인·관리자 UI도 v1엔 불필요.

# 성공 기준 (v1-prototype, 3개월 시점)

- 워크샵 **6회** 진행
- 그중 첫 사이클로 참가자 **1명이 실제 서비스 출시 1건** 도달
- **멤버쉽 2명** 확보 (출시한 1명 + 다음 회차 주인공으로 합류한 1명)
- 워크샵 6회분의 **강의 콘텐츠 누적 산출** (회당 1세트)

# 비목표

- **매스 마케팅·광고 안 함** — 알음알음 소개 chain으로만 운영
- **결제·유료 멤버쉽 안 함** — v1 무료 베타, v2에서 도입 검토
- **자동화된 신청·심사 시스템 안 함** — 2명 규모이므로 수동·대화 기반
- **UGC 메이커 로그 피드(Disquiet 식) 안 함** — v1은 운영자 큐레이팅 쇼케이스
- **모바일 앱 안 함** — web 우선, 모바일은 후속 사이클
- **멤버 로그인·관리자 대시보드 안 함** — 기존 멤버 3명(본인+진행자 2명)은 카톡으로 운영, 내부 UI 불필요

# 핵심 가설

운영 모델은 design 결과(Bsides.html "운영방식 — 한 사이클, 한 멤버, 서비스 출시") 흡수:

- **운영자(현지)가 단계별 학습자료·코칭** 제공 (아이템·기획·개발·디자인·출시·홍보 6단계)
- **멤버 한 명이 그 사이클의 주인공** — 자기 프로젝트로 따라 만들고 사이클 끝에 실제 출시 (v1 첫 멤버 = 김도현 · 도토리룸 — 원룸 계약, 빠진 특약 같이 잡아요)
- **객원 멤버는 자기 분야에서 거든다** (디자인·개발·마케팅)
- **객원 → 정식 멤버 전환 4단계**: 객원 참여 → 운영자·멤버 심사 → 약관 동의 → 정식 멤버
- **다음 사이클은 다른 멤버의 프로젝트**로 (릴레이) — 이번 사이클 객원 멤버 중 한 명이 다음 프로젝트의 주인공이 될 수도

가설:

- **H1 (릴레이 자생)**: 객원 → 정식 멤버 → 다음 사이클 주인공 자생 전환 흐름이 작동한다. (검증: v1 사이클 내 객원→주인공 전환 1건)
- **H2 (organic 유입의 충분성)**: 알음알음 소개 + 홈페이지 organic 유입(검색·외부 링크 공유)만으로도 3개월 안에 워크샵 6회 페이스 + 멤버쉽 2명 확보가 가능하다. 매스 광고 없이. (검증: 3개월 시점 지표 달성)
- **H3 (사이클 → 출시)**: 한 사이클·한 멤버 모델을 적용하면, **v1 사이클 내 주인공 멤버 1명이 출시 도달**한다. (검증: 도토리룸 출시 1건)
