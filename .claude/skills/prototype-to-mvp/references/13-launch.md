배포(12)는 인프라가 켜진 상태. 출시(13)는 **사람이 들어오는 일**. MVP 단계의 출시는 **soft launch — 작게, 한 명씩** 받는 게 본질. 본격 마케팅은 14단계.

## 1. 단계 목표

- **첫 실제 사용자 1~5명 받기** (가까운 사람·동료 메이커·잠재 타겟).
- **핵심 동작 1개가 사용자와 끝까지 굴려지나** 직접 관찰.
- **사용자 응대 창구 1개** 확립 (카톡·이메일·DM 무관).
- **첫 PMF 시그널 수집** — 정량(완주율·재방문)·정성(말로 한 줄 피드백).

## 2. 진행 절차

### 2.1 사이클 분기

- 첫 MVP 사이클(`v2-mvp`): 작게. 친한 사람 N=1부터.
- 이후 사이클(`v3-mvp-revision` 등): 가설 변경 반영 후 새 사용자군 또는 같은 군 재호출.

### 2.2 자동 점검 (AI 단독)

- `12-deploy.md` 산출물 확인: production URL 응답, 외부 접근 가능.
- 분석 1개 활성 (Vercel Analytics 등 — 12-deploy 단계 산출물).
- 사용자 응대 창구 명시됨 (사이트에 카톡·이메일 link 노출).
- 에러 모니터링 설정 (선택 — Sentry 등).

### 2.3 사용자 결정 — 누구한테 보일까?

```
출시 시작 — 첫 사용자 1~5명. 누구?

후보 카테고리:
- 가까운 사람 (가족·친구·동료) — 솔직한 피드백, 비전문가
- 동료 메이커 — 기술·UX 시각 피드백
- 타겟 사용자 (PRD 정의) — 진짜 검증
- 다 (시간 차)

이번 사이클 우선순위 1~2개만.
```

답에 따라 §2.4 진행.

### 2.4 첫 사용자 응대 (운영자 직접)

**원칙**: **자동화 X. 운영자가 직접 1:1로.** MVP 단계는 손이 필요한 영역.

각 사용자별:
1. URL 공유 + 한 줄 설명 ("이거 만들었어. 5분만 써보고 어땠는지 알려줘.")
2. 사용자 첫 시도 직접 관찰 (옆에 있으면 좋고, 화면공유나 카톡 캡쳐로도 OK)
3. 막히는 지점 즉시 수정 (사이트 작은 fix는 그 자리에서)
4. 끝까지 사용한 후 한 줄 피드백 받기

**관찰 포인트**:
- 어디서 멈췄나
- 어디서 한숨 또는 "?" 표정 나왔나
- 어떤 단어가 헷갈렸나
- 끝까지 갔다면 "다음에 또 쓸 거 같아?"

### 2.5 검증 시그널 수집

소규모라 통계는 무의미. **개별 시그널 누적** + **패턴 발견**:

| 시그널 | 좋은 지표 | 약한 지표 |
|---|---|---|
| 정성 한 줄 | "다음에 또 쓸 거 같아" / "친구한테 추천하고 싶어" | "음... 잘 모르겠어" |
| 행동 (재방문) | 묻지도 않았는데 다시 들어옴 | 한 번 보고 다시 안 옴 |
| 막힘 패턴 | 다 같은 곳에서 막힘 (수정 신호) | 사람마다 다른 곳에서 막힘 (랜덤·작은 문제) |
| 추천 의사 | "친구한테 보여줘도 돼?" | 침묵 |

→ N=3~5 사용자에서 **같은 좋은 지표가 반복**되면 본격 마케팅(14) 진입 OK.

### 2.6 launch-checklist.md 작성

`planning/cycles/v{N}-mvp/launch-checklist.md` 생성:

```markdown
---
cycle: v2-mvp
launch_date: YYYY-MM-DD

- 누구: {이름·관계}
- 일시: YYYY-MM-DD HH:MM
- 결과: {완주·중간 이탈·막힘}
- 피드백 한 줄: "..."
- 발견 패턴: {기록}

# 사용자 2 ...

# 발견 종합 (N=N 시점)
- {반복되는 좋은 지표}
- {반복되는 막힘}
- {14단계 진입 결정 여부}
```

## 3. 완료 체크리스트

- [ ] 최소 N=3 실제 사용자 받음 (운영자 자신 제외)
- [ ] 각 사용자별 launch-checklist.md 기록 완료
- [ ] 핵심 동작 완주율 ≥60% (3명 중 2명 이상)
- [ ] 사용자 응대 창구 작동 확인
- [ ] 발견 패턴 정리 (반복 좋은 지표 또는 반복 막힘)
- [ ] 14단계(PR & Marketing) 진입 결정 (또는 작은 fix 후 재시도)

## 4. 산출물 스펙

위치: `planning/cycles/v{N}-mvp/launch-checklist.md`. §2.6 구조.

## 5. 사이클 업데이트 모드

다음 MVP 사이클(`v3-mvp-revision` 등)에선:
- `launch-checklist.md` 새로 작성 (사이클별 분리)
- 이전 사이클 발견을 PRD·Architecture 입력으로 반영했는지 확인

## 6. 좋은 예 vs 나쁜 예

- **사용자 수** — 좋은: N=3~5 직접 응대. / 나쁜: 100명한테 동시 메일 ("아무도 답 안 줌" 패턴).
- **응대 방식** — 좋은: "옆에서 5분 같이 봐줄게." / 나쁜: "써보고 알려줘" (피드백 0).
- **시그널 해석** — 좋은: "3명 중 2명이 같은 곳에서 막힘 → 수정 결정". / 나쁜: "한 명이 '나쁘진 않아' 했으니 OK".
- **다음 단계 결정** — 좋은: "PMF 시그널 약함, 가설 1 재검토 + 다음 사이클 진입". / 나쁜: "일단 마케팅부터".

## 7. 사용자 응대 톤 + 인터뷰 코칭

- **톤**: SKILL.md §1.3대로 반말·친근·짧게. 출시는 ceremony 없음 — 운영자가 한 명씩 노트 만들며 진행.
- **코칭**: SKILL.md §1.4대로. 사용자가 "누구한테 보여줄지" 모호하면 후보 카테고리 제시 + "한 명만 우선 골라" 권장. 시그널 해석 모호하면 N 늘릴지·수정 먼저 할지 양자택일 제시.
