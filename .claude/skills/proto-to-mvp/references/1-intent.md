---

Intent는 후속 단계의 입력 산출물을 만든다. 모호하면 PRD·Architecture가 흔들리니 충분히 대화한다. 핵심은 **추상 질문이 아닌 한 사람의 한 사건 스토리에서 출발**하는 것 — 처음 만드는 사람에게 추상은 어렵고, 스토리는 evidence 원본이 된다.

## 1. 단계 목표

"무엇을 · 왜 · 누구를 위해 · 어떤 맥락에서 쓰는지" 정의 + 측정 가능한 **성공 기준** + 명시적 **비목표** + 검증 가능한 **핵심 가설**. 디테일은 §3 체크리스트.

플랫폼은 여기서 정하지 않는다. **사용 맥락**(시점·환경·빈도)을 충분히 적어두면 Sketch 단계에서 플랫폼이 자연스럽게 좁혀진다 — 솔루션을 미리 박지 않는 게 핵심.

## 2. 진행 절차

### 2.1 사이클 종류에 따라 분기

- **첫 사이클(v1-prototype)**: 백지 상태에서 §2.2 흐름 시작.
- **두 번째 이상 사이클(v2-mvp 이후)**: 직전 사이클의 `intent.md`와 `retro.md`를 base로 둔다. 빈 파일에서 시작 금지. **§5 사이클 업데이트 모드** 절차 따름.

### 2.2 인터뷰 흐름: 스토리 → 초안 → 확정

추상 질문은 처음 만드는 사람에게 어렵다. 한 사람의 한 사건에서 시작한다.

#### Step 1. 스토리 받기

먼저 가른다:

- **자기 경험**: 가장 최근 이 문제를 겪은 한 장면을 5W1H + 그때 어떻게 (안)해결됐는지로 200~400자.
- **타인 관찰 — 직접 대화함**: 그 사람에게서 들은 한 장면을 같은 형식으로.
- **타인 관찰 — 추측**: 🟥 진행 OK하되 모든 추출 항목을 가설로 표시. Sketch 진입 전 최소 1명 인터뷰 권장.

스토리는 산출물의 `# 출처 스토리`로 그대로 보존된다 — v2 회고 시 evidence 원본.

#### Step 2. AI가 6개 항목 초안 작성

스토리에서 §4.1의 6개 항목(문제 정의·타겟 사용자·사용 맥락·성공 기준·비목표·핵심 가설)을 채워 사용자에게 보여준다. 항목 옆에 신뢰도 라벨:

- ✅ **스토리에서 직접**: 명시된 것 (막힘 포인트·시점·장소·환경 등).
- 🟡 **추정**: 일반화·추론. 사용자 확인 필요.

**성공 기준·비목표는 빈칸으로 둔다** — founder의 의지·우선순위 결정이라 추정 금지.

#### Step 3. 사용자 확정

- ✅는 맞으면 통과, 틀리면 고침.
- 🟡는 사용자 답으로 굳히거나 검증 가설로 남김.
- 빈칸(성공 기준·비목표)은 사용자가 채움. 막히면 AI가 후보 2~3개 제시.

## 3. 완료 체크리스트 (게이트 통과 조건)

다음이 모두 충족되어야 다음 단계(Sketch)로 진입한다. 형식·예시는 §4.1 / §6 참조.

- [ ] **출처 스토리** 1단락 (누구·언제·무슨 일 + 자기경험/타인대화/추측 표시).
- [ ] **문제 정의** 작성됨 (§4.1 형식).
- [ ] **타겟 사용자** 작성됨 — "사용자·모두·누구나" 같은 모호함 X.
- [ ] **사용 맥락** 시점·빈도·환경 1줄 이상.
- [ ] **성공 기준** 측정 가능한 지표 최소 1개.
- [ ] **비목표** 최소 1개 (이유 포함).
- [ ] **핵심 가설** 1~2개 (검증 가능 형태).

체크리스트 미충족 시 사용자에게 어느 항목이 빠졌는지 알리고 보완 또는 SKILL.md §5 게이트 정책에 따라 진행.

## 4. 산출물 스펙

산출물 위치: `planning/cycles/v{N}-{label}/intent.md`

### 4.1 파일 구조

각 섹션은 정해진 **형식**이 있다. 형식이 깨지면 PRD·Architecture에서 추론이 흔들린다 — 모호한 입력에서 명확한 설계가 나올 수 없다. 작성 시 형식과 그 옆 *왜*를 같이 본다.

```markdown
---
cycle: v1-prototype
created_at: YYYY-MM-DD
updated_at: YYYY-MM-DD
---

# 출처 스토리
형식: **누구의·언제·무슨 일** 한 단락(200~400자) + 출처 표시 (자기 경험 / 타인 대화 / 타인 추측).
*왜*: 아래 6개 항목 모두의 evidence 원본. v2에서 변화 추적·새 사례 비교 시 기준이 됨. 추측이면 🟥 표시해 검증 우선순위로 둠.

# 문제 정의
형식: **"[누가]가 [맥락]에서 [원인] 때문에 [무엇]을 못한다."** 한 문단(1~2문장).
*왜 이 형식*: 주어·맥락·원인·결과가 다 들어가야 PRD에서 해결 범위를 자를 수 있다. "불편하다·불투명하다" 같은 형용사로 끝내면 무엇을 만들지 정의되지 않는다.

# 타겟 사용자
형식: **페르소나(연령·직업·경험) + 상태(지식 수준·도구·관련 경험)**.
*왜*: "사용자"라고만 적으면 디자인·기능 우선순위를 못 정한다. 실제 한 사람을 그릴 수 있을 만큼 구체. 사용 시점·장소는 아래 "사용 맥락"에 분리해 적는다.

# 사용 맥락
형식: **시점·장소 + 빈도·세션 길이 + 환경 제약(이동 중·소음·집중도·연결성·동시 작업)**.
*왜*: Sketch 단계에서 플랫폼·인터랙션 결정의 입력값. 여기 충실히 적어두면 "이 맥락이면 모바일이 강제됨" 같은 결정이 자동으로 나오고, Sketch에서 같은 질문을 다시 캐묻지 않아도 된다. 솔루션을 미리 박지 않으면서도 솔루션이 좁혀지는 길.
- 예: "출퇴근 지하철에서 주 1~2회, 5분 이내, 한 손 조작 필요, 데이터 약함."

# 성공 기준
형식: **측정 가능한 지표 + 수치 + 시점**. 최소 1개.
*왜*: 숫자 없으면 사이클 끝에서 "성공인지" 판정 불가 → 회고가 흐려지고 v2 방향이 안 잡힌다.
- 지표 1: (예: v1 종료 시점 베타 사용자 50명)
- 지표 2: ...

# 비목표
형식: **"[X] 안 함 — [이유]"**. 최소 1개.
*왜*: 욕심을 안 자르면 사이클이 끝나지 않는다. 이유까지 적어야 다음 사이클에서 "정말 계속 안 할지" 재검토 가능.
- 안 할 것 1
- 안 할 것 2

# 핵심 가설
형식: **"[조건]하면 [예측 결과]할 것이다"**. 1~2개.
*왜*: 가설 형태여야 사이클 끝에서 검증 가능. "사용자가 좋아할 것"은 검증 불가 — "X 기능이 있으면 7일 리텐션 30% 넘을 것"은 가능.
```

### 4.2 frontmatter 규칙

- `cycle`: 현재 사이클 라벨 (예: `v1-prototype`).
- `created_at` / `updated_at`: 최초 생성일 / 최근 수정일. 사이클 간 업데이트 시 `updated_at` 갱신.

## 5. 사이클 업데이트 모드 (v2 이상)

새 사이클의 `intent.md`는 직전 사이클 산출물을 base로 둔다. 백지에서 시작하지 않는다.

### 5.1 첫 질문

```
v1-prototype 회고 보니 [핵심 발견 한두 줄]였어. v2-mvp Intent 어떻게 업데이트할까?
- 출처 스토리: v1 보존 + 새 사례 추가? / 새 스토리로 교체?
- 문제 정의: 동일 / 좁힘 / 넓힘 / 바뀜
- 타겟 사용자: 동일 / 좁힘 / 넓힘 / 바뀜
- 사용 맥락: 동일 / 좁힘 / 바뀜
- 성공 기준: v1 지표 유지 / 새 지표
- 비목표: 동일 / 추가
- 핵심 가설: v1 검증 결과 / 새 가설
```

### 5.2 업데이트 원칙

- **덮어쓰기 금지**: 이전 내용을 지우지 말고, 변경 시 이유를 본문에 한 줄 메모. 예: "v1에선 X였는데 v2에선 Y로 좁힘 — 이유: 회고에서 Z 발견."
- **검증된 가설은 본문 보존**, "가설 1 (v1에서 검증됨)"으로 마킹.
- **frontmatter `updated_at` 갱신**, `cycle`을 새 라벨로 변경.

## 6. 좋은 예 vs 나쁜 예

### 6.1 문제 정의

**좋은 예** (주어·맥락·원인·결과 다 들어감):
> 자취 처음 하는 20대가 부동산 계약 직전에 비교 기준을 모르기 때문에, 어떤 특약이 빠졌는지 검증을 못한다.

**나쁜 예** ← 주어·원인 없음, 형용사로 끝남:
> 부동산 시장이 불투명해서 사용자들이 불편하다. 더 나은 경험을 제공한다.

### 6.2 타겟 사용자

**좋은 예** (페르소나 + 상태, 시점은 사용 맥락으로):
> 자취 2회 미만의 20~30대 세입자. 부동산 플랫폼 지식 없음. 계약 시 가족·친구 의견을 참고하는 편.

**나쁜 예** ← 페르소나 없음, 기능 우선순위 못 정함:
> 부동산 사용자.

### 6.3 사용 맥락

**좋은 예** (시점 + 빈도 + 환경):
> 계약 직전 1~3일, 부동산 사무실에서 받은 특약을 집·카페에서 검토. 한 손 조작 모바일, 5분 단위 짧은 세션 여러 번. 친구·가족과 메시지로 빠르게 공유. 인터넷 연결은 안정적.

**나쁜 예** ← 시점·빈도 없음, 솔루션 결정 입력값으로 못 씀:
> 필요할 때 사용.

### 6.4 성공 기준

**좋은 예** (지표 + 수치 + 시점):
> - v1 종료 시점에 베타 사용자 50명
> - 그중 30명이 실제 계약 전 앱으로 특약 검토
> - 검토 후 "도움됐다" 응답 80% 이상

**나쁜 예** ← 측정 불가:
> 사용자가 만족하는 앱.

### 6.5 비목표 (좋은 예)

> - 매물 검색 안 함 — 네이버부동산·직방으로 충분
> - 계약 자동 생성 안 함 — 법적 책임 회피
> - PC 웹 안 함 — 모바일에서 즉시성 필요

### 6.6 핵심 가설 (좋은 예)

> - 사용자가 마스터 체크리스트와 자기 특약을 대조하면 빠진 조항을 5분 내에 찾을 수 있다.
> - 친구·가족 공유 기능이 있으면 의사결정 속도가 빨라진다.

## 7. 사용자 응대 톤 + 인터뷰 코칭

톤·코칭은 SKILL.md §1.3·§1.4 따름. 핵심 동작:

- §2.2 3-step 순서 따름: 스토리 → AI 초안(✅/🟡/빈칸) → 확정. Step 건너뛰지 말 것.
- 사용자 답이 §4.1 형식 또는 §6 좋은 예에 못 미치면 빠진 부분을 짚어 되묻기 ("주어가 빠졌어, 누가 그래?", "시점·빈도가 빠졌어, 언제 얼마나 자주 써?" 같은 식).
- 빈칸·"잘 모르겠어"엔 후보 2~3개 제시.
- 정리한 산출물을 보여주고 "이거 맞아? 고칠 데 있어?" 확인.
- 모르는 부분은 `TBD: ...`로 명시.
