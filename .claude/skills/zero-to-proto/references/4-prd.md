PRD는 Intent("무엇·왜·누구")·Brand Guide("어떤 톤·시각으로")·Sketch("어떻게 쓰이는가")를 받아 **"이 사이클에서 무엇을 만들 것인가"**의 목록과 명세로 옮기는 단계다. 기술 결정(Architecture)은 다음 단계 — 여기선 What과 Why만 다룬다.

**SoT 책임** (SKILL.md §3.1): PRD는 **기능 동작·비기능·외부 의존성·제약**의 SoT. **시각 layout·컴포넌트 stacking·카피 문안은 sketch/brand SoT** — PRD에선 참조로 redirect, 본문에 직접 박지 않음. 중복이 발생하면 Designer/Engineer 핸드오프에서 충돌·재작업 비용 발생.

## 1. 단계 목표

- **기능 목록** 도출 + MoSCoW 분류 (Must/Should/Could/Won't).
- **각 Must 기능별 행동 명세** — 트리거·동작·결과·엣지 케이스.
- **비기능 요구사항** — 성능·보안·호환성·접근성·다국어 등 플랫폼에 맞는 항목.
- **외부 의존성** — 어떤 API/서비스/라이브러리에 의존하나.
- **제약조건** — 시간·예산·규제·도구 제약.

## 2. 진행 절차

### 2.1 사이클 분기

- 첫 사이클이고 `prd.md` 비어있음: 백지에서 시작. Intent + Sketch 다시 보여주고 인터뷰.
- 첫 사이클인데 이미 있음: 내용 읽고 §3 체크리스트 검증, 부족분만 보완.
- 두 번째 이상 사이클: 직전 PRD + retro 기반 업데이트. **§5 사이클 업데이트 모드**.

### 2.2 플랫폼 결정

PRD가 platform 결정·SoT의 단계. Intent의 **사용 맥락**(시점·환경·빈도)과 Sketch의 화면 흐름·인터랙션을 입력으로 명시 결정. 솔루션을 미리 박지 말고 사용 맥락에서 자연스럽게 좁힘.

**입력에서 제외**: `sketch-wireframes.md`(있으면) — 사람 review용 ASCII 시각 데모. 기술 스택·platform과 무관.

```
[intent.md 사용 맥락·Sketch 시나리오 인용해서 보여주기]

이 입력 보면 platform은 어디가 가장 자연스러울까? — `web`, `mobile`, `cli`, `library`, `desktop`, `api-server`, `other` 중 하나(메인 플랫폼).
```

후보 제시 가이드 (사용자가 "잘 모르겠어" 답할 때):

- 본업 외 시간·반응형 필요·연결 안정 → **web**
- 모바일 빈번·오프라인·푸시 → **mobile**
- 개발자 도구·터미널 사용 → **cli**
- 다른 앱이 import → **library**
- 실시간 요청 처리·서버 → **api-server**
- OS 통합·local 파일 → **desktop**

결정 후 `prd.md` frontmatter에 기록 (메인 플랫폼 하나). **Cross-platform 케이스**(Flutter·RN·Tauri·Electron 등): 메인 + `platforms` + `cross_platform_framework` 추가. 트레이드오프(코드 공유율 vs 플랫폼별 native 느낌 vs 개발 속도)는 Architecture 단계에서 세부 결정.

### 2.3 기능 도출 인터뷰

`intent.md`의 **핵심 가설**과 `sketch.md`의 **핵심 시나리오 3~5개**를 다시 사용자에게 보여주고:

```
이 가설들을 검증하고 시나리오들을 실현하려면 어떤 기능이 필요해? 떠오르는 대로 자유롭게 나열해줘. 우선순위는 다음 단계에서.
```

자유 나열 받은 뒤 두 가지 점검을 한다.

1. **핵심 기능 누락 점검** — Intent의 각 가설과 Sketch의 각 시나리오를 역산해서, 그게 동작하려면 필요한데 사용자가 안 나열한 기능을 찾는다. 예: 가설1이 "5분 내 빠진 조항 식별"인데 마스터 체크리스트 로딩·매칭 알고리즘이 안 나옴. 시나리오2가 "친구에게 공유"인데 공유 링크 생성·권한 모델이 안 나옴.
2. **공통 cross-cutting 누락 점검** — 플랫폼 무관 자주 빠뜨리는 항목: 인증·온보딩·에러 처리·로깅·설정·관측성·접근성.

발견된 누락은 사용자에게 한 번에 모아서 "이것들도 필요하지 않을까? 필요/불필요로 답해줘" 묻는다.

### 2.4 MoSCoW 분류

도출된 기능 목록을 4분류로:

```
이제 우선순위.

- Must: 이게 없으면 가설 검증 불가. 이 사이클의 핵심.
- Should: 있으면 좋은데 없어도 가설은 검증됨.
- Could: 이 사이클 외 후순위 (다음 사이클로).
- Won't: 이 사이클에서 명확히 안 함 (Intent 비목표 반영).

각 기능 어디?
```

사이클 라벨과 자연 매핑: `v1-prototype`은 가설 검증이 목적이라 Must이 적음(보통 3~7개), `v2-mvp`는 Must이 늘고 Won't이 줄어드는 식. **Must이 너무 많으면 한 번 더 가지치기 권유**.

### 2.5 Must 기능별 명세 인터뷰

각 Must 기능에 대해 4개 항목. **4항목 영역 분리 — SoT 매트릭스 따름**:

| 항목 | 영역 | SoT |
|---|---|---|
| **트리거** | 사용자 액션의 type (탭·입력·스크롤). **UI 위치·버튼 라벨은 sketch 참조** | prd (액션 type) + sketch (위치) |
| **동작** | 시스템 상태 변화·외부 호출·계산·data flow | prd 단독 |
| **결과** | 데이터 결과·외부 변화. **시각 표현·layout은 sketch 참조** | prd (data 결과) + sketch (시각) |
| **엣지 케이스** | 실패·빈 입력·타임아웃의 **시스템 동작**. **빈 상태 시각·에러 메시지 디자인은 sketch 참조** | prd (behavior) + sketch (시각) |

```
[기능명]:
- 트리거: 사용자가 뭘 했을 때 이 기능이 동작해? (액션 type — UI 위치는 sketch §화면N 참조)
- 동작: 시스템이 무엇을 해? (상태 변화·외부 호출·계산)
- 결과: 데이터·외부에 무슨 일이? (시각 표현은 sketch §화면N 참조)
- 엣지 케이스: 실패·빈·타임아웃 시 시스템 동작은? (빈/로딩 시각은 sketch §2.5 참조)
- 연결: Sketch §시나리오N / Intent 가설N
```

답이 모호하면 한 번 더 구체화. 시각·layout 정보가 답에 섞이면 "그건 sketch에서 다룰 거야 — 여기선 동작/데이터 중심으로"로 redirect.

### 2.6 비기능 요구사항 — 플랫폼 분기

§2.2에서 결정한 `prd.md` frontmatter `platform` 필드 보고 분기. **`platforms`도 있으면 메인 플랫폼 + 추가 platforms의 분기 질문 셋을 모두 적용** (예: `platform: mobile` + `platforms: [web]` → mobile 항목 + web 항목 둘 다 점검). 한 코드베이스라도 각 플랫폼 UX는 native하게 검토. 플랫폼별 기본 항목:

- **web**: 
  - **Core Web Vitals (75th percentile)** — Google 공식 기준: LCP ≤ 2.5s · INP ≤ 200ms · CLS ≤ 0.1
  - Lighthouse Performance — stage별: prototype 측정만 / mvp ≥ 80 / prod ≥ 90
  - 응답 시간 P50/P95 (api 영역)
  - 동시 접속 규모·SEO·반응형 범위·다국어
  - 접근성 WCAG 2.2 AA
- **mobile**: 앱 시작 ≤ 2s (cold) · 60fps 유지 · 배터리·오프라인·푸시·접근성·iOS/Android 일관성.
- **cli**: 실행 시간·메모리·종료 코드 컨벤션·shell 호환성(bash/zsh/fish/PowerShell).
- **library**: import 비용·의존성 footprint·문서·타입 힌트·SemVer 정책·breaking change 처리.
- **api-server**: 응답 시간(P50/P95/P99)·동시 처리·rate limit·인증 방식·로깅·관측성.
- **desktop**: 시작 시간·메모리·자동 업데이트·OS별 일관성·접근성.
- **other**: 사용자에게 "이 플랫폼에서 빠지면 안 될 비기능 항목 뭐야?" 묻고 자유 입력.

각 항목에 **구체값(숫자)** 받기. "빠르게" 같은 추상 답은 한 번 더 ("P95 5초? 1초? 200ms?"). 산업 표준 임계값(Core Web Vitals 등)은 그대로 사용 가능. 게이트 강도는 SKILL.md §5.1 stage별 매트릭스 적용.

### 2.7 외부 의존성 인터뷰

```
- 외부 API·서비스: 어떤 거? (예: Stripe·OpenAI·Firebase·Sentry)
- 라이브러리·프레임워크: 핵심 (예: React·Next.js·FastAPI)
- 인프라: 호스팅·DB·캐시·메시지큐 (예: Vercel·Postgres·Redis)
- 각 의존성에 대해: 왜 이걸 골랐어? 대안 검토했어?
```

대안 검토 안 했으면 강제 안 함 — Architecture 단계에서 다시 점검.

### 2.8 제약조건 인터뷰

```
- 시간: 이 사이클 deadline?
- 예산: 호스팅·API 비용 상한?
- 규제: 개인정보·결제·의료 등 법적 제약?
- 도구: 회사·팀에서 강제되는 도구·언어·플랫폼?
```

해당 없으면 "없음" 명시. 빈 값으로 두지 말기 — "없음"과 "안 물어봤음"은 다름.

## 3. 완료 체크리스트

- [ ] **기능 목록** 5개 이상, MoSCoW 분류됨 (Won't는 비어있어도 OK).
- [ ] **Must 기능 모두 4항목 명세** — 트리거·동작·결과·엣지 케이스.
- [ ] **각 Must이 Sketch 시나리오 또는 Intent 가설과 연결됨** (참조 번호 명시).
- [ ] **SoT 분리 점검 (UI 플랫폼)** — Must 명세에 시각 layout·컴포넌트 stacking·카피 문안이 박혀있으면 sketch/brand로 이관되어 참조 redirect 처리됨. PRD 본문엔 동작·data·엣지 동작만.
- [ ] **비기능 요구사항** 플랫폼별 기본 항목 모두 답해짐 (구체값 또는 "해당 없음").
- [ ] **외부 의존성** 목록 + 각 용도 한 줄 메모.
- [ ] **제약조건** 4카테고리(시간·예산·규제·도구) 모두 답해짐 ("없음" 포함).

## 5. 사이클 업데이트 모드 (v2 이상)

새 사이클 PRD는 직전 PRD를 base로.

### 5.1 첫 질문

```
v1 회고 보니 [핵심 발견]였어. v2-mvp PRD 어떻게 업데이트할까?

- 기능 목록: Must 추가/제거? Could → Must 승격?
- 비기능 요구사항: 숫자 상향? 새 항목 추가?
- 외부 의존성: 새 의존성? 제거?
- 제약조건: 새 deadline? 예산 변경? 규제 추가?

차례로 답해줘.
```

### 5.2 업데이트 원칙

- **Must → Won't 강등은 사유 명시 필수.** 예: "v1 회고에서 사용자가 안 썼음".
- **검증된 기능은 보존**, "(v1에서 검증됨)" 마킹.
- **숫자 변경 시 v1 값 기록**: 예 "P95 5초 → 1초 (v1 평균 3초였음)".

## 6. 좋은 예 vs 나쁜 예

핵심 차이는 **검증 가능한 구체값** vs **추상·일반론**.

### 6.1 기능 명세

**좋은 예**:
> **F1: 특약 대조** — 트리거: [붙여넣기 영역]에 텍스트 입력 후 [대조 시작] 탭. 동작: 마스터 체크리스트 18개 조항과 텍스트 비교, 누락 조항 ID 리스트 반환. 결과: 누락 조항 카드 리스트 화면 표시(조항명·중요도·설명). 엣지 케이스: 빈 입력 → 토스트 "특약을 붙여넣어 주세요". 10K자 초과 → "너무 길어요. 핵심 부분만". 연결: Sketch §시나리오2.

**나쁜 예**:
> 사용자가 특약을 붙여넣으면 빠진 조항을 알려준다.

### 6.2 비기능 요구사항

**좋은 예**:
> 성능: 대조 응답 P95 5초 이내. 보안: 사용자 텍스트 서버 저장 안 함(메모리만). 접근성: 폰트 크기 시스템 설정 따름.

**나쁜 예**:
> 빠르고 안전하고 접근성 좋게.

### 6.3 외부 의존성

**좋은 예**:
> Anthropic Claude API — 특약 분석 LLM. 대안: GPT-4. 이유: 한국어 법률 텍스트 정확도 비교 시 Claude 우위. 비용: 월 $30 예상.

**나쁜 예**:
> AI API 사용.

## 7. 사용자 응대 톤 + 인터뷰 코칭

- **톤**: SKILL.md §1.3대로 반말·친근·짧게. 기능 도출 단계에서 너무 많이 나열되면 "다 만들 수는 없어 — 핵심 가설 검증에 진짜 필요한 것만" 한 번 끊어주기.
- **코칭**: SKILL.md §1.4대로. 사용자가 기능 명세 4항목(트리거·동작·결과·엣지 케이스) 다 못 채우는 게 정상. 빠진 항목 1~2개씩 차례로 되묻기. "엣지 케이스 모르겠어" 답엔 플랫폼 패턴 기반 후보 제시(예: 빈 입력·타임아웃·권한 없음·데이터 없음). AI가 §6.1 형식으로 정리해 보여주고 확인 받기. 비기능 요구사항 숫자도 사용자가 모르면 플랫폼 표준값 후보 제시(예: web P95 응답 1~5초). 모르는 부분은 `TBD: ...`로.
