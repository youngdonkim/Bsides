Sketch 단계는 Intent에서 정의한 "무엇·왜·누구"를 **사용자 인터랙션의 가시적 형태**로 옮기는 단계다. 디자인 완성도가 아니라 "이 소프트웨어가 어떻게 쓰이는가"의 골격을 합의하는 게 목적. 손그림 수준이어도 OK.

**Brand Guide도 input**: 직전 단계 `brand-guide.md`의 voice·essence·금지 사항·시각 무드·Tokens(컬러·타이포·spacing·motion)를 받아 카피·시각 placeholder를 처음부터 brand 정합으로 박는다. **이 단계 진행 중 brand-guide의 §8(차별 시각 시그널)·§9(카피 패턴)을 화면 컨텍스트 보고 보강**한다 — brand-guide는 두 단계(Brand Guide → Sketch)에 걸쳐 완성되는 산출물.

## 1. 단계 목표

- **사용자 플로우**: 처음부터 끝까지 사용자가 어떤 순서로 무엇을 거치는가.
- **핵심 시나리오 3~5개**: User Story 형식. "[누구]로서 [무엇]을 [왜]하고 싶다."
- **인터랙션 형태**: 플랫폼에 따라 다름 — 와이어프레임·명령어 예시·코드 예시·API 호출 예시 중 적절한 것.

**여기서 다루지 않는 것** (Design 단계에서 Claude Design이 자동 확장): 인터랙션 상태(hover·focus·disabled)·디자인 시스템·다국어 레이아웃·다크모드. **이 단계는 골격만**.

**SoT 책임**: SKILL.md §3.1 SoT 매트릭스에 따라 sketch가 SoT인 영역:
- 화면 layout · 컴포넌트 stacking
- 시나리오 · 플로우 · 화면 간 전환
- **화면별 엣지 케이스** (빈·로딩·에러 등) — stage별 강도 차별 (§2.5 참조)

PRD엔 시각·layout 정보를 박지 않고 sketch 참조로 redirect. 중복 발생 시 sketch가 진실의 원천.

## 2. 진행 절차

### 2.1 사이클 종류에 따라 분기

- **첫 사이클이고 sketch 산출물 없음**: 백지에서 시작. `intent.md`와 `brand-guide.md`를 base로 인터뷰.
- **첫 사이클인데 sketch 산출물 이미 있음**: 내용 읽고 §3 체크리스트 검증. 부족한 부분만 보완.
- **두 번째 이상 사이클**: 직전 sketch + retro 기반으로 업데이트. **§5 사이클 업데이트 모드** 따름.

### 2.2 인터뷰 첫 질문 — 사용자 플로우

`intent.md`의 **타겟 사용자**와 **문제 정의**를 사용자에게 다시 보여주고 묻는다. 동시에 `brand-guide.md`의 voice·essence·금지 사항을 head에 두고 인터뷰 톤·placeholder 작성에 적용.

```
intent에서 [타겟 사용자]가 [문제]를 푼다고 했지. 그 사람이 이 소프트웨어를 처음 만나서 끝까지 쓰는 동안 어떤 순서로 뭘 하는지 한 번 그려보자.

- 시작점: 어디서 알고 들어와?
- 처음 5분 안에 뭘 해?
- 핵심 작업이 뭐야? (목적 달성하는 그 순간)
- 끝낼 때 뭘 가지고 나가?
- 다시 돌아와서 또 쓰는 시나리오가 있어?
```

답을 받아 플로우 다이어그램 텍스트(또는 단계 리스트)로 정리. 사용자가 답이 모호하면 한 번 더 구체화 ("처음 5분이 너무 모호해. 첫 화면에서 뭘 봐? 무슨 버튼을 눌러?").

### 2.3 핵심 시나리오 인터뷰

```
이제 가장 중요한 시나리오 3~5개만 골라보자. User Story 형식으로:
"[누구]로서 [무엇]을 [왜]하고 싶다."

너무 일반적이면 무용지물 — 구체 상황·트리거·기대결과까지 포함해줘.
```

답을 받으면 한 줄 한 줄 검증. 너무 일반적이면("사용자로서 앱을 쓰고 싶다") 다시 구체화 요청.

### 2.4 플랫폼별 인터랙션 형태

플랫폼에 따라 가시화 방식이 다르다. Sketch는 platform 미정 OK — Intent **사용 맥락**(시점·환경·빈도) 기반으로 메인 플랫폼 가설을 잡고 그 형태로 그림. **확정·SoT는 PRD에서** (`references/4-prd.md` §2.2). cross-platform 가능성(예: web + mobile 둘 다)이 보이면 메인 + 추가 형태를 모두 그려도 됨 (예: 모바일 + 웹 와이어프레임 둘 다).

- **UI (web/mobile/desktop)**: 핵심 화면 3~7개의 ASCII 와이어프레임(또는 Figma·손그림 링크). 화면당 진입 경로·주요 컴포넌트·다음 화면 전환 트리거. 화면 간 이동 시퀀스. **카피·시각 placeholder는 `brand-guide.md`의 voice·카피 패턴·금지 사항을 input으로 적용**해 처음부터 brand 정합으로 박음. 화면 구성이 정해지면 brand-guide.md §8(차별 시각 시그널)·§9(카피 패턴)을 화면 컨텍스트(Hero·CTA·푸터 등) 기준으로 보강 update.
    - **★ ASCII 와이어프레임은 별도 파일** (`sketch-wireframes.md` 또는 `sketch/wireframes.md`)에 분리. **사람 review 전용** — Claude Design 핸드오프에 미포함. 이유: ASCII가 layout anchor 효과로 Claude Design 창의성·brand 정합 자유도를 제한할 위험. Sketch 본문엔 시나리오·플로우·화면별 진입 경로·주요 컴포넌트·전환만 박고 layout 직관은 wireframes 파일에서 사람이 빠르게 검토.
- **CLI**: 핵심 명령 3~5개의 사용 예시. 각각 사용자 입력·예상 출력·실패 케이스. 여러 명령 조합 순서.
- **library**: 핵심 사용 케이스 3~5개의 호출 예시 코드(가짜 코드 OK). 라이브러리가 노출하는 함수·클래스를 어떻게 호출하는지. 다른 코드와의 통합 시나리오.
- **api-server**: 핵심 엔드포인트 3~7개의 호출 예시. 메서드·경로·요청 샘플·응답 샘플. 인증 흐름.
- **other**: 사용자에게 "이 소프트웨어를 누가·어떻게 쓰는지 가장 잘 보여주는 형태가 뭐야?" 묻고 답에 맞춰 위 4가지 중 가까운 형태 또는 사용자 제안 형태로.

### 2.5 화면별 엣지 케이스 (UI 플랫폼만) — Stage별 강도

sketch가 엣지 케이스의 SoT. PRD엔 박지 않음 (SKILL.md §3.1).

| Stage | 화면별 엣지 강도 |
|---|---|
| `v*-prototype` | **핵심 1개만** — 보통 "빈 상태" (콘텐츠 0개·첫 진입 등). 화면당 1줄 메모로 충분 |
| `v*-mvp` | **5종** — 빈·로딩·에러·권한 거부·네트워크 오프라인. 각 화면별 메시지·복구 경로 |
| `v*-prod` | 5종 + 인터랙션 상태 (hover·active·disabled·focus·loading) + 데이터 부분 실패 |

prototype에 5종 다 박으면 placeholder 폭증 (화면 3 × 5 = 15) — 검증 사이클 부담. 핵심 1개부터 시작.

## 3. 완료 체크리스트

다음이 모두 충족되어야 다음 단계(PRD)로 진입.

- [ ] **사용자 플로우** 처음부터 끝까지 단계 리스트 또는 다이어그램으로 정리됨.
- [ ] **핵심 시나리오** 3~5개. User Story 형식. 각각 구체 상황·트리거·기대결과 포함.
- [ ] **인터랙션 형태** 플랫폼에 맞춰 그려짐 (와이어프레임·명령어 예시·서버 API 호출 예시·라이브러리 사용 예시 코드 중 하나 이상).
- [ ] 시나리오와 인터랙션이 **연결됨** — 시나리오 1번이 어느 화면·명령·API에 해당하는지 추적 가능.
- [ ] **화면별 엣지 케이스 — stage별 강도** (§2.5 참조). prototype은 화면당 핵심 1개 이상.
- [ ] **brand-guide.md §8·§9 보강 완료** — 화면 컨텍스트(Hero·CTA·푸터 등)에 맞춰 차별 시각 시그널·카피 패턴이 brand-guide.md에 추가됨 (UI 플랫폼만).
- [ ] (플랫폼 추가 질문 답이 있으면) 해당 내용도 기록됨.

체크리스트 미충족 시 SKILL.md §5 게이트 정책에 따라 사용자에게 선택지 제시.

## 4. 산출물 스펙

기본 위치:
- `planning/cycles/v{N}-{label}/sketch.md` — 시나리오·플로우·화면별 컴포넌트·전환·매핑 표. **Claude Design 핸드오프 input**.
- `planning/cycles/v{N}-{label}/sketch-wireframes.md` — **사람 review 전용** ASCII 와이어프레임. Claude Design 핸드오프 미포함.

두 파일 분리가 디폴트 (UI 플랫폼인 경우). 분리 이유 — ASCII layout이 Claude Design의 brand 정합 free explore를 anchor로 제한할 위험 방지.

화면 수가 많거나 Figma·손그림 등 이미지 첨부가 필요하면 `sketch/` 폴더로 확장:
```
planning/cycles/v{N}-{label}/sketch/
├── README.md           ← 진입점, 플로우·시나리오 정리 (Design 핸드오프 input)
├── flow.md             ← 사용자 플로우 (다이어그램·단계)
├── scenarios.md        ← 핵심 시나리오 (User Story)
├── wireframes.md       ← ★ 사람 review 전용 ASCII 와이어프레임 (Design 핸드오프 미포함)
├── screens/            ← 화면별 상세 (선택)
│   ├── 01-onboarding.md
│   ├── 02-home.md
│   └── ...
└── images/             ← Figma export, 손그림 사진 등 (선택)
```

### 4.1 단일 파일 구조

```markdown
---
platform: web | mobile | cli | library | desktop | api-server | other
cycle: v1-prototype
created_at: YYYY-MM-DD
updated_at: YYYY-MM-DD
---

# 사용자 플로우
처음 진입 → ... → 끝.
단계 리스트 또는 텍스트 다이어그램.

# 핵심 시나리오
1. **[제목]** — [누구]로서 [무엇]을 [왜]하고 싶다.
   - 트리거: ...
   - 기대결과: ...
2. ...

# 인터랙션 형태
플랫폼별 §2.4 형식으로.
```

## 5. 사이클 업데이트 모드 (v2 이상)

새 사이클의 sketch는 직전 사이클 산출물을 base로 둔다.

### 5.1 첫 질문

```
v1-prototype 회고를 보니 [핵심 발견 한두 줄]였어. 이번 v2-mvp의 sketch는 어떻게 업데이트할까?

- 사용자 플로우: [v1과 동일 / 단계 추가 / 단계 제거 / 재구성]
- 핵심 시나리오: [v1 시나리오 유지 / 새 시나리오 추가 / 기존 시나리오 수정]
- 인터랙션 형태: [화면 추가 / 명령어 추가 / API 추가 / 다른 변경]

위 3개에 대해 차례로 답해줘.
```

### 5.2 업데이트 원칙

- **덮어쓰기 금지**: 이전 내용 지우지 말고, 변경 시 이유 한 줄 메모. 예: "v1에선 X였는데 v2에선 Y로 — 이유: 회고에서 사용자가 Z 어려워함."
- **검증된 시나리오**: 본문 보존, "(v1에서 검증됨)" 마킹.
- **frontmatter `updated_at` 갱신**, `cycle`을 새 라벨로.

## 6. 좋은 예 vs 나쁜 예

핵심 차이는 **구체성·검증 가능성·시작-끝 명확함**(좋은) vs **추상·검증 불가·일반론**(나쁜).

- **사용자 플로우** — 좋은: 진입 트리거부터 핵심 작업·재방문 시나리오까지 단계별 구체. / 나쁜: "사용자가 앱에 들어와 사용하고 만족하며 나간다".
- **User Story** — 좋은: 구체적 페르소나·트리거·"5분 안에 3개" 같은 측정값. / 나쁜: "사용자로서 편하게 쓰고 싶다".
- **인터랙션 형태** — 좋은: §2.4 플랫폼 형식대로 실제 입력·출력·필드·버튼이 박힘. / 나쁜: "버튼 누르면 결과가 나옴".

플랫폼별 구체 예시가 필요하면 사용자 맥락(`intent.md`)에 맞춰 즉석에서 만들어 보여준다.

## 7. 사용자 응대 톤 + 인터뷰 코칭

- **톤**: SKILL.md §1.3대로 반말·친근·짧게. 한 번에 모든 화면·시나리오 다 던지지 말고 답을 받으면 "오케이, 다음" 식으로. 그림 그리기 부담스러워하면 "글로 쭉 써도 돼. 내가 ASCII로 옮길게" 같이 진입 장벽 낮춤.
- **코칭**: SKILL.md §1.4대로. 사용자 답이 §6 좋은 예 패턴(구체성·시작-끝 명확함)에 못 미치면 빠진 부분 짚어 되묻기. "잘 모르겠어" 답엔 후보 제시. AI가 ASCII 와이어프레임/코드/명령어 형식으로 옮긴 뒤 확인 받기. 모르는 부분은 `TBD: ...`로.
