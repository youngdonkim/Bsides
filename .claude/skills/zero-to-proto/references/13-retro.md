회고는 사이클의 **종착점**이자 **다음 사이클의 시작점**이다. Intent의 핵심 가설이 검증됐는지, 무엇이 잘됐고 아쉬웠는지, AI 자동화가 어디서 실패했는지를 정리. 이 회고가 다음 사이클(v2-mvp 등)의 Intent 첫 질문에 그대로 입력으로 들어간다.

## 1. 단계 목표

- **가설 검증 결과**: Intent 핵심 가설 → 검증됨 / 일부 / 미검증 / 새로 발견.
- **성공 기준 측정값**: PRD 비기능·성공 지표 → 실제 값 vs 목표 비교.
- **잘된 점·아쉬운 점**: 결정·기술·워크플로우.
- **AI 자동화 실패 지점**: 어느 phase에서 needs_review·error·blocked 자주 발생.
- **다음 사이클 입력**: Intent·PRD·Architecture 업데이트 사항.
- **워크플로우 개선 제안** (선택): zero-to-proto 스킬 자체 피드백.

## 2. 진행 절차

### 2.1 사이클 분기

- 첫 사이클(v1-prototype): 가설 검증 위주. 짧게.
- 두 번째 이상(v2~): + 실 사용 데이터·사용자 만족도·운영 메트릭.

### 2.2 자동 데이터 수집 (AI 단독)

AI가 사이클 모든 산출물·로그를 읽고 데이터 추출. 인터뷰 없이.

**소스**:
- `intent.md` → 핵심 가설·성공 기준·비목표
- `prd.md` → Must 기능·비기능 요구사항 지표
- `architecture.md` → 결정한 스택·구조
- `design/migration-analysis.md` → 마이그레이션 공수 추정 vs 실제
- `build/index.json` → phase별 status·started_at·completed_at·needs_review/error/blocked 발생 횟수
- `build/phase{N}-output.json` → external error 발생률
- `qa-report.md` → 통합 테스트 통과/실패·실패 카테고리·이슈 수정 내역
- `deploy-checklist.md` → 배포 결과·URL
- `git log` → commit 수·작업 기간

**자동 추출 결과**:

```
사이클 통계 (자동 수집):
- 빌드 phase: 9개 (성공 9, 평균 12분/phase)
- needs_review 발생: 2회 (phase 4 보안, phase 7 DB 스키마)
- error 발생: 1회 → 1회 재시도 후 성공
- blocked 발생: 0
- 외부 장애([external]): 0
- 통합 테스트: 13/13 통과 (인라인 fix 1, 새 phase 추가 1)
- git commits: 24개
- 작업 기간: 2026-04-29 ~ 2026-05-04 (5일)
```

### 2.3 retro.md 초안 작성 (AI 단독)

자동 데이터로 retro.md 초안을 **직접 작성**. 사용자 인터뷰는 초안 review 단계로 미룸 — 추상 질문 4개에 답하는 것보다 **구체 초안 review가 효율·정확도 ↑** (의사가 검사 결과 차트 들고 와서 spot 확인하는 패턴).

**원칙**:
- 자동 추출되는 모든 항목은 초안에 채움
- 자동 추출 안 되는 항목은 **`TBD: <무엇을 확인할지>` 마커**로 명시. **추측으로 채우지 말기.**
- frontmatter `status: draft` — 사용자 확정 전까지

**자주 TBD가 되는 카테고리** (자동 추출 거의 안 됨):
- 가설 검증 결과 (운영 메트릭·사용자 피드백 필요)
- 성공 기준 실제 값 (운영 메트릭 필요)
- 새로 발견된 가설 (사용자 주관)
- 잘된 점·아쉬운 점 중 dynamics·취향 영역
- 워크플로우 개선 제안 중 우선순위

**자동 추출되는 카테고리** (TBD 안 함, 추출 못 하면 "데이터 없음" 명시):
- 빌드 phase 통계 (`build/index.json`)
- needs_review·error·blocked 발생 수 (build outputs)
- PR·commit 수 (`git log`)
- 산출물·rules·hooks·skills 변화 추적
- AI 자동화 실패 지점 (build outputs 분석)
- 발견 사항 룰화 판정 (산출물 변화 + git history로 추론)

**초안 구조**: §2.4 retro.md 구조 그대로 채움.

### 2.3.1 발견 사항 — 룰화 판정 3분류

cycle 진행 중 발견된 수정사항·이슈·미흡 항목을 다음 3분류로 판정. **룰화는 비용**(LLM context 소비·트리거 매핑 약화) — 가치 통과한 것만 룰화.

| 분류 | 기준 | 처리 |
|---|---|---|
| **룰화** | (a) **재발 위험**: 다음 cycle/유사 작업에서 같은 함정 가능성 + (b) **횡단 가치**: 이 프로젝트뿐 아니라 유사 프로젝트에도 적용 가능 | `.claude/rules/<topic>.md` 신규 또는 기존 룰 보강. paths frontmatter로 트리거 매핑. CLAUDE.md 컨벤션 한 줄 추가 검토 |
| **spot fix** | 일회성 수정. 같은 패턴 재발 가능성 낮음 | 코드만 수정. 룰화 X |
| **코멘트** | 사용자·팀 dynamics·취향·일회성 판단 | 어디에도 박지 않음. retro.md "잘된 점·아쉬운 점"에만 |

**판정은 둘 다 통과해야 룰화** — 재발 위험만 있고 횡단 가치 없으면 spot fix. 횡단 가치만 있고 재발 위험 낮으면 코멘트로.

발견 사항 표 예시 (retro.md에 포함):

```markdown
## 발견 사항 — 룰화 판정

| # | 내용 | 분류 | 처리 |
|---|---|---|---|
| 1 | 카카오 OAuth adapter wrap 패턴 누락으로 첫 가입 실패 | 룰화 | `.claude/rules/kakao-auth-share.md` 신규 + ADR-0003 |
| 2 | 다크모드에서 카카오 옐로 island 처리 누락 | 룰화 | `.claude/rules/ui-ux-baseline.md` "외부 브랜드 island" |
| 3 | review 페이지 redirect 경로 오타 | spot fix | 코드만 수정 |
| 4 | 마스코트 톤 "도토리야"가 사용자 N=3에서 "이상하다" 코멘트 | 코멘트 | retro 아쉬운 점 |
```

### 2.5 TBD 채우기 (선택적 인터뷰)

§2.3 초안을 사용자에게 보여주고 **TBD 항목만** 답 받음. 고정 4개 질문이 아니라 **초안 TBD 개수만큼** N개.

```
retro.md 초안 끝났어. TBD [N]개 답해줘:

1. {TBD 항목 1} → {무엇을 확인할지}
2. {TBD 항목 2} → ...
...

답 한 번에 줘도 되고 하나씩 줘도 OK.
```

답이 모호하면 SKILL.md §1.4 코칭으로 한 번 더 구체화 요청. 사용자가 "모르겠어"면 후보 2~3개 제시. TBD 답이 사용자한테 부담스러우면 "보류 — 사유" 명시 허용.

### 2.6 retro.md 최종화

TBD 답을 반영해 최종화:
- 각 TBD 마커 → 사용자 답으로 대체 (또는 "보류 — 사유" 명시)
- frontmatter `status: draft` → `status: confirmed`
- 사용자에게 최종 확인

### 2.7 사이클 종료 처리

retro.md 확정 후:
- `build/index.json`의 사이클 상태 표시 (또는 별도 cycle 메타 갱신)
- git tag 생성 (선택): `git tag v1-prototype && git push --tags`
- 사용자에게 다음 사이클 진입 의향 묻기:

```
v1-prototype 회고 끝났어. 다음 사이클 갈래?
- 새 사이클 시작 (v2-mvp): retro.md 핵심 발견 base로 Intent 업데이트부터 시작
- 일단 멈춤: 회고 결과 반영해 더 검토하거나 사용자 피드백 더 모음

어느 쪽?
```

새 사이클 진입 시 `references/cycle-triggers.md` §5 절차로 (v2 폴더 생성 + v1 산출물 base 복사 + Intent 업데이트 인터뷰).

- [ ] **TBD 채우기** (§2.5) — 사용자가 모든 TBD 답함 (또는 "보류 — 사유" 명시).

- [ ] **다음 사이클 입력** Intent·PRD·Architecture 업데이트 항목 모두 결정됨.

- [ ] **(선택) git tag** 생성됨.

## 4. 산출물 스펙

위치: `planning/cycles/v{N}-{label}/retro.md`. 위 §2.4 구조 그대로.

**frontmatter 필수 필드**:
- `cycle`: 사이클 라벨 (v1-prototype 등)
- `created_at`: ISO date
- `status`: `draft` (§2.3 작성 직후) → `confirmed` (§2.6 사용자 확정 후)

**핵심 원칙**: retro.md는 다음 사이클의 직접 입력. 1-intent.md §5 사이클 업데이트 모드 첫 질문이 retro의 "핵심 발견"·"다음 사이클 입력"을 그대로 가져다 씀.

## 5. 사이클 업데이트 모드

회고 자체가 사이클 업데이트 메커니즘이므로 별도 분기 없음. 매 사이클 끝에 동일 절차로.

다만 사이클 라벨별 깊이:
- **prototype**: §2.3 4개 질문 그대로. 짧게.
- **mvp**: + 실 사용자 N명 피드백·NPS·이탈률
- **production**: + SLA 달성률·인시던트·운영 비용·고객 지원 티켓

## 6. 좋은 예 vs 나쁜 예

- **가설 검증** — 좋은: "가설1 검증됨, 평균 3.7분 (목표 5분 이내)". / 나쁜: "잘 됨".
- **AI 자동화 실패** — 좋은: "phase 4·7에서 needs_review 발생, 보안·DB 스키마 변경 트리거. 검토에 사용자 시간 30분". / 나쁜: "AI가 헷갈렸음".
- **다음 사이클 입력** — 좋은: "Must에 '실시간 알림' 추가, 사유: v1 회고에서 사용자 8/12명이 '결과를 알림으로 받고 싶다' 답함". / 나쁜: "기능 추가".
- **TBD 표기** (§2.3 초안 시점) — 좋은: "H3 도토리룸 출시 도달: TBD — 사용자 확인 필요 (운영 메트릭 없음)". / 나쁜: "H3: 잘 됐을 거임" (자동 추출 못 한 걸 추측으로 채움).

## 7. 사용자 응대 톤 + 인터뷰 코칭

- **톤**: SKILL.md §1.3대로 반말·친근·짧게.
- **흐름**: 자동 데이터 수집 → **AI가 초안 직접 작성 (TBD 마커 포함)** → 사용자에게 초안 보여주고 TBD 답 받기 → 최종화 → 사용자 확정.
- **코칭**: SKILL.md §1.4대로. 사용자가 TBD 답 모호하면 "측정값 있어? 사용자 피드백 있어?" 구체화. 모호 답이 계속되면 자동 데이터 base 후보 제시(예: error 자주 난 부분 → Architecture 보완 후보, qa-report 다음 사이클로 미룬 이슈 → 새 Must 후보).
- **TBD 처리**: 초안(§2.3) 단계엔 TBD OK. 최종화(§2.6) 시점엔 **TBD 남기지 말고 사용자 답으로 대체 또는 "보류 — 사유" 명시**.
